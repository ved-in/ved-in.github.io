I've read the Raft paper twice and nodded along both times without being able to say exactly why a randomized election timeout prevents split votes. So I wrote Quorum: a three-node Raft implementation with no networking library, no persistence, and no ambitions beyond running on my laptop long enough to watch leader election happen.

## Leader election, actually happening

Each node is a small state machine with three states:

The part that finally made it click wasn't the state diagram, it was adding deliberate jitter to the election timeout and watching two nodes race each other into candidacy, split the vote, time out, and re-run the election with a *different* random delay until one of them won cleanly. The randomness isn't a detail - it's the entire mechanism that keeps the cluster from livelocking.

```go
func (n *Node) runElectionTimer() {
    timeout := randomBetween(150*time.Millisecond, 300*time.Millisecond)
    if n.sinceLastHeartbeat() > timeout {
        n.becomeCandidate()
    }
}
```

## What I got wrong first

My first version had every node use the *same* fixed timeout. It deadlocked almost every run - every follower became a candidate at exactly the same moment, every vote split, forever. It's an obvious bug once you've seen it and a genuinely confusing one before you have.
